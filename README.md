# Billing API

HTTP API, отдающее по Merchant ID оборот и заработанную комиссию за период.
Данные приезжают из CSV, нормализуются в минимальные юниты (халалы/центы) и
хранятся в MongoDB целыми числами. API тоже отдаёт минимальные юниты.

Два бинаря: `cmd/importer` загружает фид и завершается, `cmd/api` только читает.
Разделение не косметическое — см. [Импорт и API — разные процессы](#импорт-и-api--разные-процессы).

## Запуск

```
docker compose up --build -d
```

Поднимается MongoDB, дожидается healthcheck, отрабатывает `importer` (заливает
CSV из `CSV_PATH` и выходит), и только после его успешного завершения стартует
`api` на `:8080`.

```
curl "localhost:8080/merchants/M-1001/summary?from=2026-03-01T00:00:00%2B03:00&to=2026-04-01T00:00:00%2B03:00&currency=SAR"
```

## Ручки

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/merchants/{merchant_id}/summary` | оборот и комиссия за период |
| GET | `/merchants` | список merchant_id, постранично |
| GET | `/healthz` | liveness |
| GET | `/readyz` | readiness, пингует Mongo |

Неверный метод на существующем пути — 405 с заголовком `Allow`, а не 404:
«метода нет» и «пути нет» — разные проблемы, и отправлять клиента искать опечатку
в URL, когда опечатка в глаголе, незачем.

### `GET /merchants/{merchant_id}/summary`

| Параметр | Обязательный | Описание |
|---|---|---|
| `from` | нет | начало периода, **включительно**, RFC3339 с явным офсетом |
| `to` | нет | конец периода, **исключительно**, RFC3339 с явным офсетом |
| `currency` | нет | код ISO 4217, фильтр по валюте |

Период — полуинтервал `[from, to)`: соседние месяцы стыкуются без нахлёста и
без дыры. Оба параметра опциональны, без них — за всё время.

Офсет обязателен. Голая дата `2026-03-01` отклоняется с 400: в этом фиде есть
строки в пределах трёх часов от обеих границ месяца, и молчаливый выбор
таймзоны сдвинул бы итог. Ответ эхом отдаёт период, приведённый к UTC.

Плюс в офсете нужно кодировать как `%2B`: в query-string голый `+`
декодируется в пробел, и `from=2026-03-01T00:00:00+03:00` приезжает как
`2026-03-01T00:00:00 03:00`. Ошибка на этот случай узнаёт пробел и говорит
именно про кодирование, а не повторяет общую подсказку про формат.

`currency` проверяется по таблице ISO 4217, а не по форме «три латинские буквы».
Опечатка вроде `SAT` формально проходит проверку формы, не совпадает ни с чем и
вернулась бы строкой нулей — то есть «здесь нет оборота» вместо «вы спросили
несуществующую валюту». Теперь это 400.

```json
{
  "merchant_id": "M-1001",
  "period": { "from": "2026-02-28T21:00:00Z", "to": "2026-03-31T21:00:00Z" },
  "totals": [
    {
      "currency": "SAR",
      "turnover_minor": 29861737,
      "refunds_minor": 2411218,
      "net_minor": 27450519,
      "fee_minor": 510941,
      "sale_count": 118,
      "refund_count": 8,
      "fee_missing_count": 2
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `turnover_minor` | сумма продаж, строки с `amount > 0` |
| `refunds_minor` | сумма возвратов, положительной величиной |
| `net_minor` | `turnover_minor - refunds_minor` |
| `fee_minor` | суммарная комиссия по всем строкам корзины, включая возвраты; никогда не отрицательная |
| `fee_missing_count` | сколько строк в этой корзине пришли без `fee` |

Все поля `*_minor` — целые числа в минимальных юнитах валюты своей строки.

Ненулевой `fee_missing_count` означает, что `fee_minor` занижен: столько-то
строк пришли из источника без комиссии и дали ноль. Поле нужно, чтобы это
занижение было видно в ответе, а не только в логах импорта. Это верхняя оценка
занижения: у `T-20074` комиссия пустая, но её возврат `T-20103` несёт
ненулевую — см. следующий абзац.

**Комиссия на строке возврата.** `fee_minor` складывает `fee` по всем строкам
корзины, включая возвраты. В фиде 11 возвратов, у девяти комиссия нулевая, у
двух положительная: `T-20103` (48.1659) и `T-20210` (34.9687). Принятая
трактовка: комиссия на строке возврата — это плата за проведение самого
возврата, поэтому она прибавляется к `fee_minor`, а не вычитается из него как
сторно комиссии по исходной продаже.

Трактовка не выведена из данных, а выбрана: колонки с типом операции в фиде
нет, и оба прочтения одинаково правдоподобны. Цена ошибки видна на `T-20165`
(продажа 2056.98, `fee` 34.9687) и её возврате `T-20210` с той же комиссией:
если это всё-таки сторно, то по полностью возвращённой транзакции комиссия
учтена дважды. На M-1001/SAR за всё время такие строки дают 8314 минорных
юнитов из 513780 — 1.6% `fee_minor`. Когда источник начнёт различать типы
операций, поле стоит разложить на `fee_sales_minor` и `fee_refunds_minor`:
тогда обе цифры видны по отдельности и выбор трактовки перестаёт быть нашим.

**Почему массив, а не одно число.** У `M-1001` в фиде три валюты: SAR, USD, EUR.
Курсов в данных нет, поэтому единого кросс-валютного итога не существует и
выдумывать его API не будет. Нужен ровно один объект — передайте `currency`.
С явным `currency` ответ всегда содержит одну строку: при отсутствии транзакций
она заполнена нулями, чтобы клиенту не приходилось отдельно разбирать пустой
массив.

**Сколько запросов в Mongo.** Непустой ответ — один: строки в результате сами
доказывают, что мерчант существует. Второй запрос делается только когда
агрегация вернула пусто, и только чтобы отличить «в этом периоде ничего не было»
от «такого мерчанта нет». Отдельной коллекции мерчантов нет: существование здесь
означает ровно «есть хотя бы одна транзакция».

### `GET /merchants`

| Параметр | По умолчанию | Описание |
|---|---|---|
| `limit` | `100` | размер страницы, 1..1000 |
| `after` | пусто | курсор: вернуть id строго больше указанного |

```json
{ "merchant_ids": ["M-1001", "M-1002", "M-1003"], "next_after": "M-1003" }
```

`next_after` отсутствует на последней странице. Ручка не использует `distinct`:
его результат — один BSON-документ, и на 16 МБ он упирается в потолок, обойти
который постранично нельзя. Здесь `$group` по `merchant_id` с курсором, префикс
индекса `merchant_currency_ts` покрывает и `$match`, и группировку.

### Ошибки

Приходят единым конвертом:

```json
{ "error": { "code": "invalid_period", "message": "from must be strictly before to" } }
```

| Код | Статус |
|---|---|
| `invalid_period`, `invalid_currency`, `invalid_merchant_id`, `invalid_limit` | 400 |
| `not_found`, `merchant_not_found` | 404 |
| `method_not_allowed` | 405 |
| `client_closed_request` | 499 |
| `internal_error` | 500 |
| `storage_unavailable` | 503 |
| `timeout` | 504 |

Причина 5xx пишется в лог сервиса, наружу не утекает.

Три исхода неудачного похода в хранилище разведены намеренно. Наш собственный
`REQUEST_TIMEOUT` — это 504 и `WARN`: запрос дольше, чем сервис разрешает, но не
дефект. Клиент, отвалившийся раньше ответа, — это 499 (нестандартный код nginx) и
`INFO`: 5xx тут не при чём, иначе алерт по доле пятисоток будет звенеть на каждой
закрытой вкладке. И только всё остальное — 500 с логом причины.

## Нормализация

**Деньги.** Парсер работает по строке и не проходит через `float64`:
`1608.17 * 100` в двоичной плавающей точке даёт `160816.99...` и усекается в
неверное целое. `amount` в фиде с двумя знаками, `fee` — с четырьмя, поэтому
комиссия округляется до минимального юнита **half away from zero**
(`5.3550 → 536`). Режим зафиксирован тестом: восемь значений `fee` в фиде лежат
ровно на половине юнита, результат наблюдаем.

**Масштаб берётся из валюты, а не из константы.** `internal/money` держит таблицу
ISO 4217: у SAR, USD и EUR два знака после запятой, у JPY — ноль, у KWD и BHD —
три. Захардкоженная сотня на этом фиде отработала бы правильно и молча завысила
бы иеновую строку в сто раз, как только такая появится. Таблица закрытая:
неизвестный код валюты — не повод угадать «наверное, два знака», а повод
отбраковать строку.

Побочный эффект округления на строку: сумма округлённых комиссий расходится с
округлённой точной суммой максимум на пол-юнита на транзакцию. Если понадобится
сверка до копейки на больших объёмах — рядом кладётся точное значение ×10⁴, а
округление делается уже от суммы.

**Время.** В фиде смешаны `Z` и `+03:00`. Всё приводится к UTC при импорте, в
Mongo лежит `ISODate` в UTC.

**MCC** хранится строкой: `0742` и `0763` теряют ведущий ноль как число.

## Что сделано с грязными данными

Импорт валидирует каждую строку. Не прошедшие уходят в коллекцию
`import_rejects` с номером строки, исходным содержимым и причиной — чтобы
потерянные данные были видны, а не растворялись в тотале.

| Ситуация | В фиде | Решение |
|---|---|---|
| Дубль `transaction_id` с идентичным содержимым | 4 (`T-20093`, `T-20177`, `T-20308`, `T-20405`) | схлопывается, считается в `duplicates_skipped` |
| Дубль `transaction_id` с расходящимся содержимым | 0 | отбраковка: молча выбирать победителя нельзя |
| Пустой `fee` | 4 (`T-20074`, `T-20107`, `T-20345`, `T-20458`) | строка импортируется с `fee = 0` и флагом `fee_missing`, счётчик виден в ответе |
| Непарсящийся `fee` | 0 | отбраковка: строка испорчена, а не неполна |
| Отрицательный `fee` | 0 | отбраковка: комиссия по определению неотрицательна |
| Неизвестный код валюты | 0 | отбраковка: масштаб минимального юнита неизвестен |
| Возврат, `amount < 0` | 11 | учитывается отдельным полем, не вычитается из оборота |
| Ненулевая `fee` на строке возврата | 2 (`T-20103`, `T-20210`) | трактуется как плата за проведение возврата, прибавляется к `fee_minor` |

Два дубля (`T-20177`, `T-20405`) записаны в разных таймзонах, но указывают на
один и тот же момент UTC — сравнение идёт уже по нормализованным значениям,
поэтому они распознаются как дубли, а не как конфликт.

Из 493 строк принимается 489: минус 4 дубля.

**Почему пустой `fee` не отбраковывается.** Изначально такая строка
выбрасывалась целиком, и это давало ошибку в расчёте. `T-20074` (M-1001, SAR,
2833.29) уходила в отбраковку из-за пустой комиссии, а её возврат `T-20103`
(−2833.29) проходил валидацию и попадал в базу. Пара «продажа/возврат»
разрывалась пополам: возврат в книгах есть, продажи нет. `net_minor` у M-1001
занижался на 2833.29 SAR.

Корень в том, что решение принималось построчно, а дефект затрагивал одно поле:
`amount` в этой строке валиден и связан с другой строкой. Поэтому отбраковка
осталась только для строк, непригодных целиком (битый timestamp, непарсящийся
`amount` или `fee`, отрицательный `fee`, неизвестная валюта), а неполная строка
импортируется с нулевой комиссией и флагом.

## Хранение

Коллекция `transactions`:

```
_id             ObjectId    // штатный монговский
transaction_id  string      // уникальный индекс
merchant_id     string
ts              date        // всегда UTC
amount_minor    int64
fee_minor       int64
currency        string
mcc             string
fee_missing     bool        // в источнике комиссия была пустой
source          string      // файл, из которого приехало текущее содержимое
ingested_at     date        // когда именно этот прогон его записал
first_seen_at   date        // когда id увидели впервые, $setOnInsert
```

Последние три поля — происхождение строки. Без них на вопрос «из какой загрузки
эта цифра и когда она изменилась» ответить нечем, а это первый вопрос, когда итог
выглядит неправдоподобно. `import_rejects` такой аудит имел с самого начала —
странно было держать его на отбракованных строках и не держать на деньгах.

Индексы:

- `transaction_id` — уникальный. Импорт делает `UpdateOne` с `upsert` по
  этому полю, поэтому повторный прогон обновляет строки, а не плодит их.
  Уникальность здесь не украшение: без неё два параллельных upsert'а по ещё не
  существующему ключу создадут две записи.
- `{merchant_id, currency, ts}` — покрывает `$match` саммари и `$group`
  в листинге мерчантов.

`$set` вместо полной замены документа — чтобы `first_seen_at`, записанный один
раз через `$setOnInsert`, пережил все последующие загрузки: `source` и
`ingested_at` двигаются, момент первого появления id — нет.

Агрегация саммари считается на стороне Mongo (`$match` → `$group` → `$sort`),
поэтому непустой ответ — один round trip независимо от числа подходящих строк.

## Импорт и API — разные процессы

`cmd/importer` читает CSV, пишет транзакции и отбраковку, завершается. `cmd/api`
только читает: `CSV_PATH` он не использует, и если переменная всё-таки задана —
пишет об этом WARN и игнорирует.

Раньше импорт жил внутри API и выполнялся на старте. Это давало две проблемы:

- **Битый фид ронял живой сервис.** Любая ошибка импорта возвращалась наверх и
  завершала процесс. Поменялся заголовок CSV, не примонтировался файл — API не
  поднимается, хотя данные в Mongo целы и он мог бы их отдавать. В Kubernetes это
  CrashLoopBackOff при полностью здоровой базе.
- **Сервис нельзя было масштабировать.** Два пода, импортирующих одновременно,
  конкурируют за уникальный индекс `transaction_id`, и один падает на BulkWrite.
  Отсюда были `replicas: 1` и `strategy: Recreate`.

Теперь `api` не пишет вообще, а загрузка — отдельный Job, который в CI
отрабатывает до раската. В Deployment стоит `replicas: 1` — это размер
прототипа, а не ограничение: поды больше не конкурируют за уникальный индекс,
поэтому реплики можно поднимать, а `strategy` вернулась к обычному
RollingUpdate вместо `Recreate`.

## Конфигурация

| Переменная | По умолчанию | Кто читает | Назначение |
|---|---|---|---|
| `HTTP_ADDR` | `:8080` | api | адрес HTTP-сервера |
| `MONGO_URI` | `mongodb://localhost:27017` | оба | подключение к Mongo |
| `MONGO_DB` | `billing-test-assignment` | оба | база |
| `CSV_PATH` | пусто | importer | путь к CSV, обязателен для импорта |
| `STARTUP_TIMEOUT` | `60s` | api | таймаут на подключение и индексы |
| `IMPORT_TIMEOUT` | `10m` | importer | таймаут на весь прогон импорта |
| `REQUEST_TIMEOUT` | `10s` | api | таймаут обработки одного запроса |
| `SHUTDOWN_TIMEOUT` | `10s` | оба | таймаут graceful shutdown |

`CSV_PATH` резолвится в той файловой системе, где идёт процесс. В compose это
путь внутри контейнера (`/app/testdata/transactions.csv`, файл кладётся туда
Dockerfile-ом), при локальном запуске из GoLand — путь в репозитории
(`testdata/transactions.csv`).

## Запуск из GoLand

В `.run/` лежат готовые конфигурации, они подхватываются проектом сами:

| Конфигурация | Что делает |
|---|---|
| `Mongo (compose)` | поднимает только базу |
| `Importer (local)` | поднимает Mongo и заливает CSV из репозитория |
| `API (local)` | поднимает Mongo и запускает backend локально |
| `Stack (compose)` | весь стек в докере: mongo → importer → api |
| `Tests (unit)` | `go test ./...` |
| `Tests (with Mongo)` | интеграционные тесты хранилища с `MONGO_TEST_URI` |
| `Tests (e2e)` | поднимает стек и сверяет ответы API с CSV |

`Importer (local)` и `API (local)` объявляют `Mongo (compose)` как before-launch
задачу. На чистой базе порядок такой: один раз `Importer (local)`, дальше
`API (local)` сколько угодно раз.

## Разработка

```
make test              # юнит-тесты, интеграционные и e2e скипаются
make test-integration  # агрегация против живой Mongo из compose
make test-e2e          # цифры из CSV против поднятого API
make import            # локальный прогон импорта в Mongo из compose
make lint              # gofmt -l + go vet
make up                # docker compose up --build -d
make down              # docker compose down -v
```

### End-to-end

`e2e/` считает суммы прямо из `testdata/transactions.csv` и сверяет их с ответами
работающего сервиса. Ожидаемые значения считаются **независимой реализацией** на
`math/big.Rat`, а не через `internal/money`: переиспользование боевого парсера
означало бы, что одна и та же ошибка проходит с обеих сторон и тест ничего не
доказывает. По той же причине таблица знаков после запятой в оракуле своя —
общая таблица не поймала бы неверную строку в таблице. Формы ответов объявлены
в самом тесте, поэтому переименование JSON-тега обязано его уронить.

Тесты пропускаются, пока не задан `API_BASE_URL`; сервис по этому адресу должен
быть поднят на том же CSV:

```
make up && make test-e2e
```

Покрывается: каждый мерчант в каждой валюте, вызов без фильтра валюты, пять
периодов (включая обе границы марта и открытые с одной стороны интервалы),
листинг мерчантов постранично и целиком, инвариант «у каждого возврата есть своя
продажа».

Тесты проверены мутациями — подменой боевого кода с проверкой, что тест краснеет:
суммирование возвратов в оборот, усечение вместо half-up, возврат к отбраковке
строк с пустым `fee`. Все три ловятся.

Тесты хранилища ходят в настоящую Mongo: арифметика саммари живёт в
aggregation pipeline, и мок проверял бы только мок. Они пропускаются, пока не
задан `MONGO_TEST_URI`, каждый прогон работает в своей базе и удаляет её за
собой.

Из зависимостей — только драйвер MongoDB. HTTP-роутинг на `net/http`:
`ServeMux` из Go 1.22 умеет `GET /merchants/{merchant_id}/summary` и
`r.PathValue`, внешний роутер не нужен. 405 получается регистрацией пути дважды —
с методом и без: более специфичный паттерн выигрывает у catch-all.

## CI

`.github/workflows/ci.yaml` — на каждый push в `master` и на каждый pull request:

| Job | Что делает |
|---|---|
| `lint` | `gofmt -l` (падает при непроформатированных файлах) и `go vet` |
| `test` | юниты плюс интеграционные тесты хранилища против сервис-контейнера `mongo:7` |
| `e2e` | поднимает `docker compose`, ждёт `/readyz`, сверяет ответы API с CSV |

`e2e` в CI ловит тот класс ошибок, ради которого он и написан: расхождение
между цифрами в файле и цифрами в ответе.

## Deploy

`.github/workflows/deploy.yaml` — на push в `master`: собирает образ, пушит в
`ghcr.io`, прогоняет Job импорта, раскатывает в кластер DigitalOcean `k8s` в
namespace `billing-test-assignment` и дожидается `rollout status`.

Импорт идёт **до** раската и его падение останавливает деплой: выкатить новый код
поверх наполовину загруженной коллекции хуже, чем не выкатить вовсе. Job
пересоздаётся (`delete --ignore-not-found` перед `apply`), потому что pod template
у Job неизменяем.

Манифесты в `deploy/`: Job импорта, Deployment, Service, Ingress на
`billing-test-assignment.shopgrip.ru` (nginx + cert-manager `letsencrypt`). Плейсхолдер
`image: busybox` подменяется в CI на конкретный тег и в Job, и в Deployment.

### Что нужно завести один раз

Namespace CI не создаёт: деплой только раскатывает в уже существующий. Порядок
на чистом кластере такой.

1. Секрет репозитория `DIGITALOCEAN_CI_TOKEN` — токен DO с доступом к кластеру.
2. Пакет `ghcr.io/<owner>/billing-test-assignment` должен быть публичным.
   Иначе поду нужен `imagePullSecrets`, которого в манифесте намеренно нет.
3. Namespace:

```
kubectl create namespace billing-test-assignment
```

4. Секрет с адресом Mongo. В манифесте его нет, потому что репозиторий
   публичный, а строка подключения называет внутреннюю инфраструктуру:

```
kubectl -n billing-test-assignment create secret generic mongo --from-literal=uri='mongodb://<host>:27017'
```

5. DNS: `A billing-test-assignment -> <IP ingress-балансировщика>`.

Шаги 3 и 4 нужны до первого запуска деплоя, иначе он упадёт.

## Что осталось за рамками прототипа

- Импорт читает файл целиком в память. Для фида такого размера это нормально;
  для потокового объёма нужен батчевый проход, а дедупликацию отдать
  уникальному индексу.
- Отбраковка видна только в Mongo и в логах Job — наружу `import_rejects` не
  отдаётся. Ручка `GET /imports/{source}/rejects` доделала бы фичу.
- Аутентификации нет. Сервис только читает, но в публичный интернет он смотрит
  через ingress без ограничений — для прототипа приемлемо, для продакшена нет.
- Метрик и correlation-id нет, только структурированный лог.
- Кросс-валютных итогов нет — нет источника курсов.
- `$sum` в пайплайне декодируется в `int64`. При переполнении int64 Mongo молча
  отдаёт double; порог — 9.2·10¹⁶ в мажорных единицах, то есть недостижим, но
  при переходе на суммы за годы это стоит проверить.
